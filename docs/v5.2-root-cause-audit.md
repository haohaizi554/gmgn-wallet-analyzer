# V5.2 Root Cause Audit

日期：2026-09-17  
范围：`app/`、`tests/`、`docs/`、`main.py`、`requirements.txt`、`.env.example`  
Baseline：`python -u -m unittest discover -s tests -q` → **80 tests OK**（约 8.7s）

本审计只解释当前真实调用链，不把 V5.2 目标当成已经落地。

---

## 调用链（当前）

```text
AnalysisJobEngine._run
  └─ DataOrchestrator.from_config
  └─ WalletAnalysisService.analyze
        1. GMGN wallet_stats          ← 阻塞主流程
        2. GMGN wallet_profits        ← 阻塞主流程
        3. DataOrchestrator.collect_wallet_swaps
              Helius Wallet History?  ← 有 Key 才进
                └─ 失败则 RPC fallback（仅当 helius.enabled）
              else Moralis iter_wallet_swaps
              else 返回空 WalletSwapIndex
        4. 若 swap_index.by_token 为空
              ActivityCollector.collect_report_window  ← GMGN activity
        5. 无异常 → TaskStatus.SUCCESS
```

`ProviderPriorityRegistry` 存在，但 `collect_wallet_swaps` **没有调用** `request_capability()` / `priority.order()`。

---

## 1. 为什么真实运行顺序是 `GMGN stats → GMGN profits → Moralis → GMGN activity`

`WalletAnalysisService.analyze()` 在采集历史之前同步调用：

- `_load_stats(request)` → GMGN `wallet_stats`
- `_load_profit(request)` → GMGN `wallet_profits`

然后才 `orchestrator.collect_wallet_swaps()`。

因此日志必然先出现 GMGN stats（常见约数秒），再出现 Moralis。这不是调度器随机顺序，是服务层写死的串行顺序。

GMGN activity 出现在第四步：当 `collect_wallet_swaps` 返回空 `by_token` 时，服务层把空结果当成“没有索引”，回退 `ActivityCollector`（GMGN）。

---

## 2. 为什么 Moralis 10054 后直接使用 GMGN history

三层叠加：

1. **HTTP 无重试**  
   `app/providers/http.py` `HTTPAdapter(max_retries=0)`。`ConnectionResetError(10054)` 被 `requests` 包成 `RequestException`，一次失败立刻 `ProviderError(retryable=True)`，没有 0.5/1/2s 的 3 次 attempt。

2. **Orchestrator 吃掉失败并返回空索引**  
   Moralis 分支 `except ProviderError` 只打 warning，然后 `return WalletSwapIndex(wallet=wallet)`（`success` 语义不存在，空 list 与失败无法区分）。

3. **服务层把空索引当成“需要 GMGN”**  
   `if swap_index and swap_index.by_token:` 为假 → `ActivityCollector.collect_report_window`。

另外：V5 的 `collect_wallet_swaps` 把 RPC fallback **嵌在 `if helius.enabled` 里**。没有 Helius Key 时，Moralis 失败后 **根本不会走 Solana RPC**，只会落到 GMGN。

---

## 3. 为什么 GMGN 返回空后直接 `SUCCESS tokens=0`

- GMGN `wallet_activity=[]` 没有 `HistoryCoverage`。
- `ActivityCollector` 把空页当成采集结束。
- `analyze()` 收尾：`status = TaskStatus.SUCCESS`，条件只看 token 分析是否抛错 / `failed` 计数。
- 日志：`SUCCESS 分析完成 tokens=%s`。
- **没有** “请求失败所以 []” 与 “完整覆盖且 0 笔” 的区分。
- 空结果没有 `verified_empty`，却被当成真实 0 Token。

这是比 429 更危险的失败模式：生成一份看似成功、可能完全错误的 Excel。

---

## 4. 当前 Moralis retry 是否存在

**不存在业务级 retry。**

| 层 | 行为 |
|----|------|
| `requests.HTTPAdapter` | `max_retries=0` |
| `HttpProviderMixin.http_request` | 网络异常立即 raise |
| 401 / 403 | 立即 `ProviderAuthError`（这一点符合 V5.2：不应网络重试） |
| 429 | 立即 `ProviderRateLimitError` + cooldown，无 Retry-After 后的有限重试 |
| 5xx | 立即 `ProviderError`，`circuit.record_failure`，无 3 次退避 |
| Moralis `_request_rotating` | 只在 401/429 时换 Key，不处理 10054 |

Circuit breaker 阈值是 3 次失败 / 默认 60s OPEN，但每次 `http_request` 只有 1 次 attempt，所以 10054 不会在同一次调用内重试。

---

## 5. 当前 Provider Priority 是否真的被业务主链使用

**基本没有。**

`DEFAULT_PRIORITY.WALLET_SWAPS` 仍是：

```text
helius → solana_rpc → moralis → gmgn
```

`request_capability()` 会读这个表，但钱包主索引 `collect_wallet_swaps` 手写 Helius-first，且 RPC 仅在 Helius enabled 时运行。

配置层：`ENABLE_MORALIS` 默认 `_truthy(..., False)`。即使 `.env` 有 Key，只要 flag 为 false，Moralis `has_capability` 为假，主链不会用它。

结论：Priority Registry 是文档，不是运行时主链。

---

## 6. 是否仍存在 legacy ActivityCollector 绕过 Orchestrator

**是，而且是空结果的默认出口。**

条件：

- `orchestrator is None`（V4 部分测试 / `gmgn_only` 以外的旧路径）
- 或 `collect_wallet_swaps` 返回空 `by_token`（失败、未配置、verified empty 全算空）
- 或 orchestrator 抛异常被 `except` 打成 `swap_index = None`

然后 `ActivityCollector.collect_report_window` / `collect_token_history` 直接打 GMGN。`ENABLE_GMGN_DEEP_HISTORY_FALLBACK=false` **挡不住这条路径**，因为服务层没有看这个 flag（只在 `use_index and not deep_gmgn_history` 时跳过 per-token GMGN；空索引时仍会 GMGN 周期采集）。

---

## 7. 当前 Warm Cache 如何 merge

Helius 路径：

- `get_wallet_history_state` 若 `bottom_complete` 且有 `newest_signature`，传入 `until_signature`
- `collect_history(until_signature=...)` 只拉 **new head**
- `_persist_history_state` 用本次 `transactions[0]` / `[-1]` **整表覆盖** oldest/newest

因此第二次同步如果只返回新交易 C：

```text
oldest=C, newest=C   # 错误，A 被丢掉
返回的 WalletSwapIndex 只有 new head
```

没有 `wallet_history_events` 表，无法 `cached body + new head → full index`。

Moralis 路径：每次 `iter_wallet_swaps` 全量分页，不读 history state，也没有增量停止。

## 8. start_ts / end_ts 是否真的生效

**部分生效，语义错误。**

- Orchestrator 把 `request.start_time` 传给 Moralis `fromDate`。这会 **在索引层丢掉窗口外的 First Buy**。
- 若走 orchestrator 且 `by_token` 非空：`report_trades = swap_index.swaps` **不再过滤窗口**（全部进入报告）。
- `_analyze_token` 内部会对 `history` 再按 `start_time/end_time` 切 `report_token_trades`（买入/卖出笔数），但 Token 集合已在上层按 lifetime `by_token.keys()` 决定。
- 结果：可能漏掉窗口外 First Buy，或把窗口外 Token 整批带进 7d 报告，取决于走哪条采集路径。

验收用例「100 天前 Buy + 3 天前 Sell，7d 报告必须出现该 Token，report trades 只有 Sell，First Buy 仍是 100 天前」当前 **不能保证**。

## 9. SWAP BUY / SELL 当前如何判断

`app/providers/helius/parsers.py` `classify_token_event`：

```python
if declared == "SWAP" or (token_delta > 0 and quote_delta < 0):
    return "buy"
if declared == "SWAP" or (token_delta < 0 and quote_delta > 0):
    return "sell"
```

`declared == "SWAP"` 在第一个分支就返回 BUY。所有 Helius/RPC 解析出的 SWAP 都会变成 BUY。这是 P0。

Moralis 路径依赖接口自己的 `transactionType`（buy/sell），不走这段；Helius/RPC fallback 会中招。

---

## 10. Quote Asset 当前如何建模

`history_to_swaps`：

- 把 SOL / WSOL / USDC / USDT 的 delta **全部 `sum()`**
- Quote leg 固定 `symbol="SOL"`、`address=WSOL`

USDC 成交会被写成 SOL 成本。没有 `QuoteLeg` / `NormalizedSwap`。  
Moralis `SwapLeg` 本身有 `symbol`/`usdAmount`，但 RPC/Helius 转换层丢掉了真实 quote。

`swap_to_trade`：仅当 quote 是 SOL/WSOL 时填 `cost_sol`；USDC 的 `cost_usd` 依赖 Moralis `usdAmount`。若 USD 字段丢失且 quote 被改成 SOL，成本会错。

## 其它已确认缺口（实施时必须修）

| 项 | 现状 |
|----|------|
| ProviderResult / HistoryCoverage | 不存在。Provider 多返回 `list` |
| DataQualityGate | 不存在。没抛异常 = SUCCESS |
| Helius 硬依赖 | GUI 启动/开始分析把 Helius 当默认主路径；`HeliusProvider.optional = False` |
| GMGN 空 ≠ verified empty | 无 coverage |
| 多 Token Account | `get_token_balance` 已 sum ATA；`parse_verified_transaction._token_balance` **只取第一个账户** |
| Gas | First Buy 核验时用 `meta.fee`；未核验则可能空 |
| DEX batch 30 | DexScreenerProvider 仍 batch，应保持 |
| Token Created vs Pool Created | `resolve_creation_times` 已拆；pairCreatedAt 已作 pool |
| `.env.example` | 仍是 V5 Helius-primary / `ENABLE_MORALIS=false` |

---

## 根因一句话

V5 把 Helius 写成主链，但运行环境没有 Helius Key；Moralis 10054 没有重试；RPC fallback 被包在 Helius enabled 里；空 `[]` 没有 coverage；服务层把空索引送去 GMGN，再把 GMGN 空页当成 SUCCESS 0 Token。

V5.2 必须把主链改成 **Moralis → Solana RPC →（可选 Helius）**，GMGN 只做辅助，并且用 `HistoryCoverage.verified_empty` 卡住假成功。
